\section{Measuring Fallback Value}
\label{sec:method}

We evaluate a specified fallback at a recorded decision. Every comparison starts from the same history and environment.

\subsection{Setting}
\label{sec:setting}

\paragraph{Tasks and agents.} We use \tautwo{} in text mode. The main development panel has 58 retail and 27 airline tasks. We also evaluate 80 telecom development tasks and a holdout of 34 telecom tasks. The holdout protocol was fixed before any agent ran those tasks. % src: manifests/fork/splits_v1.json
The agents are Qwen3-4B-Instruct and Qwen3-8B with thinking disabled; a second family, Mistral-Small-3.2-24B, is a scope check (Appendix~\ref{app:scope}). % nocheck: model name
One greedy Qwen3-30B-A3B-Instruct user simulator serves all agents. % src: ../cloq_work/sims/*.json (hf_id); docs/FINAL_EXPERIMENTS.md
Retail and airline success requires a final-database match and normal termination. It excludes some official communication checks. Telecom uses the official task-basis success. BFCL multi-turn and ALFWorld have no LLM user; each item is evaluated once (Appendix~\ref{app:setup}).

\paragraph{Quantization and serving.} Q is a simulated (fake-quantized) checkpoint served with BF16 compute on the same path as B. The main W4 settings use GPTQ \citep{frantar2023gptq} or AWQ-style scaling \citep{lin2024awq}, with group size 128 and a BF16 KV cache. Calibration uses BF16 agent trajectories from 57 retail and airline tasks, disjoint from the development panel. Separate KV8 configurations quantize the cache to INT8 while retaining BF16 weights. Additional quantization settings test the range of upgrade values (Appendix Table~\ref{tab:qconfig}). % src: runs/a6k2_q4_gptq_w4_d1_f01/quantization.json; runs/a6k2_q8_awq_w4_f01/quantization.json; runs/a6k2_q8_kvq_int8_f01/quantization.json; manifests/a6k2/q4/calib_fp_traj_c1.json
B and Q run on vLLM \citep{kwon2023vllm} with batch-invariant kernels \citep{he2025defeating} and deterministic compilation in separate server processes (no shared prefix cache). A configuration is a model with a quantization setting. Each replicate, called a \emph{block}, runs Q over the task pool with a fresh session-identifier line in the system prompt. A \emph{unit} is one task in one block.

\subsection{Four branches on one state}
\label{sec:estimands}

\paragraph{Frozen state.} Before Q's decision $t$, we restore state $s_t$. It contains the full message history, the user simulator's visible conversation, and the used step and error budgets. Replaying the recorded tool calls rebuilds the environment and user-device databases. We save the state before running any branch. Their prompt tokens are identical.

\paragraph{Four branches.} Let $\YY{XY}\in\{0,1\}$ denote task success when X supplies the current action and Y continues, with X, Y $\in\{\mathrm{B},\mathrm{Q}\}$. All branches start with the same remaining budget. Each upgrade is compared with QQ: replace this step ($G$), take over from the next step ($H$), or do both ($F$). Figure~\ref{fig:case} defines these contrasts. % nocheck: notation {0,1}
A \emph{rescue} occurs when the upgrade succeeds and QQ fails; a \emph{damage} is the reverse. Their sum is \emph{turnover}, and their difference is \emph{net gain}. These quantities measure task consequences. Additional notation appears in Appendix~\ref{app:names}.

\paragraph{The action being replaced.} An action is a complete assistant turn, including its language and structured tool calls. Its message and tool results enter the subsequent history. The continuing model then makes every later decision. Thus BQ asks whether borrowing B's action helps Q finish; QB asks whether B can improve the trajectory after Q's action; BB asks whether changing both helps. The four branches are complete task executions. Each task--block unit receives one intervention. A router that can trigger repeatedly has a different policy value, requiring an end-to-end evaluation.

\paragraph{Reference interventions.} We repeat the design with Q$'$ in place of B. Q$'$ is another GPTQ-W4 checkpoint of the same model, built by resampling states and activation rows from the same calibration trajectories. The Q episodes, tasks and prompt blocks stay fixed. This reference tests how much change can occur at fixed bit width. It covers Qwen3-4B and Qwen3-8B GPTQ-W4, with GPTQ-W3 as a stress check. Its protocol was fixed before outcomes were read. Section~\ref{sec:sameprec} also compares the action sources at shared states and changes the key order of Q's own tool call.

\subsection{Making the counterfactuals auditable}
\label{sec:replay}

The branches differ in the intended intervention, with history, environment and remaining budgets restored before execution. Outcome-independent no-op audits check that restoring a state preserves its original result: all 924 sampled development states and all 1202 holdout divergent states matched. These checks make the paired comparisons trustworthy under the tested greedy, dense-BF16 serving stack; Appendix~\ref{app:setup} gives the acceptance rules and Appendix~\ref{app:prereg} the holdout protocol.

\subsection{Sampling and inference}
\label{sec:states}

\paragraph{State sources.} A first divergent state is the earliest Q-history decision where B and Q differ in action kind, tool calls or normalised arguments. Wording alone does not qualify. Ordinary states are selected by a fixed hash before action generation, one per task and block. A \emph{common state} is an ordinary sampled state at which several action sources are compared; Figure~\ref{fig:method}b distinguishes the state sources. Full-pool rates include every task--block unit, counting no divergence as zero effect; mode and pattern analyses condition on divergent states. We write $\Gall$ for the full-pool action-only net gain, and $G$ for its average on divergent states. % src: docs/insights/FORK_PROTOCOL.md §15 amendment 1
Contrasts are paired within a configuration. The W4 pool averages four configuration-specific effects equally on the fixed development task set; each configuration supplies its own first divergences. It is not a comparison of configurations at identical decisions. Only complete blocks enter. % nocheck: interval rule as in archived method L39


\paragraph{Intervals and interpretation.} The main figures use new-task intervals, which resample both tasks and prompt blocks, and the holdout uses its registered confidence level. Fixed-pool intervals and the adjusted common-state reading appear in the appendix. An interval containing zero leaves the effect unresolved; equivalence requires a separate test. Captions specify the confidence levels. Each branch measures one realised outcome under the specified greedy stack. A rescue or damage labels that paired execution; its stability across different user or prompt conditions is a separate quantity.
